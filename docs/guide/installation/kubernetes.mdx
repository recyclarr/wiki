Recyclarr has an official Helm chart that runs the Recyclarr server in Kubernetes. It is published
to the GitHub Container Registry as an OCI chart:

```txt
oci://ghcr.io/recyclarr/charts/recyclarr
```

The chart version is the Recyclarr version: chart `9.0.0` deploys Recyclarr `9.0.0`. A new chart
version comes out with each Recyclarr release, and fixes to the chart itself ship with the next
release. By default the chart uses the `ghcr.io/recyclarr/recyclarr` image tagged with that same
version.

## Example {/*#example*/}

This example keeps the server's [API key][api-key] and the Sonarr and Radarr API keys in Secrets you
create:

```bash
kubectl create secret generic recyclarr-api-key \
  --from-literal=api-key="$(openssl rand -hex 32)"
kubectl create secret generic recyclarr-servarr-keys \
  --from-literal=SONARR_API_KEY=your-sonarr-api-key \
  --from-literal=RADARR_API_KEY=your-radarr-api-key
```

```yml
# values.yaml
apiKey:
  existingSecret: recyclarr-api-key
configs:
  files:
    sonarr.yml: |
      sonarr:
        main:
          base_url: http://sonarr:8989
          api_key: !env_var SONARR_API_KEY
    radarr.yml: |
      radarr:
        main:
          base_url: http://radarr:7878
          api_key: !env_var RADARR_API_KEY
settings:
  content: |
    server:
      schedule:
        cron: 0 4 * * *
env:
  - name: TZ
    value: America/Santiago
envFrom:
  - secretRef:
      name: recyclarr-servarr-keys
```

```bash
helm install recyclarr oci://ghcr.io/recyclarr/charts/recyclarr -f values.yaml
```

The server syncs on its [built-in schedule][schedule]. `TZ` sets the schedule's time zone (default
`UTC`). The pod becomes ready after the first TRaSH Guides download, which can take a few minutes.

## API Key {/*#api-key*/}

The server does not start without an [API key][api-key], so the chart requires one. Set exactly one
of these; `helm install` fails if you set neither or both:

- `apiKey.existingSecret`: the name of a Secret you manage, for example one created by hand or by
  External Secrets Operator. The chart reads the key from the Secret's `api-key` entry. Set
  `apiKey.existingSecretKey` to use a different entry.
- `apiKey.value`: the key itself, at least 32 characters. The chart creates a Secret for it. This
  puts the key in your values file, so prefer `existingSecret` when the values file is in version
  control.

The chart mounts the key as a file and sets `RECYCLARR_API_KEY_FILE` to its path. The server reads
the file on every request, so you can rotate the key in the Secret without restarting the pod.

The chart also sets `RECYCLARR_API_KEY` to an empty value, which the server treats as unset. In
Kubernetes an `env` entry wins over the same name from `envFrom`, so a Secret loaded with `envFrom`
can contain a `RECYCLARR_API_KEY` entry without stopping the server from starting. The server
ignores that entry and always uses the key from `apiKey`. `helm install` fails if you set
`RECYCLARR_API_KEY` or `RECYCLARR_API_KEY_FILE` in `env`.

## Configuration Files {/*#config-files*/}

The chart mounts your files read-only in the [config directory][file-structure]. Each source can
come from your values or from a ConfigMap you manage, but not both:

| Values                                             | Mounted at             |
| -------------------------------------------------- | ---------------------- |
| `configs.files` or `configs.existingConfigMap`     | `/config/configs/`     |
| `includes.files` or `includes.existingConfigMap`   | `/config/includes/`    |
| `settings.content` or `settings.existingConfigMap` | `/config/settings.yml` |

`configs.files` and `includes.files` map each file name to its contents. File names in
`configs.files` must end in `.yml` or `.yaml`. `settings.content` holds the contents of
`settings.yml`. Without it, the server uses default settings. Write every file's contents as a
string (with `|`), as in the [example](#example). Helm then passes YAML tags such as `!env_var`
through unchanged.

In an existing ConfigMap, each key is a file name and its value is the file's contents. A settings
ConfigMap must have a `settings.yml` key. If you generate it with a Kustomize `configMapGenerator`,
set `disableNameSuffixHash: true`, because Kustomize does not rewrite names inside Helm values.

The server applies edits to its YAML configuration files without a restart (see
[Configuration Changes][client-server-changes]), but reads `settings.yml` and environment variables
only when it starts. `helm upgrade` restarts the pod when files or the API key in your values
change. When you change a configs or includes ConfigMap you manage, Kubernetes updates the mounted
files after a short delay, and the server picks up the edit. After you change a settings ConfigMap
you manage, a Secret the container reads through `env` or `envFrom`, or a file mounted with
[extra volumes](#extra-volumes), restart the Deployment yourself or let [Reloader][reloader] do it.
Reloader reads an annotation on the Deployment, which you set with `deploymentAnnotations`:

```yml
deploymentAnnotations:
  reloader.stakater.com/auto: "true"
```

Reloader then restarts the pod when a ConfigMap or Secret the pod uses changes.

## Environment Variables {/*#env*/}

`env` and `envFrom` add environment variables to the container, usually Sonarr and Radarr API keys
that your configuration reads with [`!env_var`][env-var]. Pass a whole Secret with `envFrom`, as in
the [example](#example), or single entries with `env`:

```yml
env:
  - name: SONARR_API_KEY
    valueFrom:
      secretKeyRef:
        name: recyclarr-servarr-keys
        key: SONARR_API_KEY
```

To keep the keys in a `secrets.yml` file instead, mount it with [extra volumes](#extra-volumes).

## Extra Volumes {/*#extra-volumes*/}

`extraVolumes` adds volumes to the pod, and `extraVolumeMounts` mounts them in the server container.
Both take the standard Kubernetes volume and volume mount lists. Use them for files the chart does
not manage, such as a `secrets.yml` file or a CA bundle.

A `secrets.yml` file in the config directory makes [`!secret`][secrets] references and the
[implicit][implicit] `<instance>_api_key` lookups work. Create a Secret from the file:

```bash
kubectl create secret generic recyclarr-secrets --from-file=secrets.yml
```

Then mount it at `/config/secrets.yml`:

```yml
extraVolumes:
  - name: secrets
    secret:
      secretName: recyclarr-secrets
extraVolumeMounts:
  - name: secrets
    mountPath: /config/secrets.yml
    subPath: secrets.yml
    readOnly: true
```

Mount single files into `/config` with `subPath`. The chart mounts its own files inside `/config`,
and a volume mounted at `/config` itself would replace that whole directory. A file mounted with
`subPath` does not update when its source changes, so restart the pod after you change the Secret,
or use [Reloader](#config-files).

## Storage {/*#storage*/}

The chart gives the [state directory][state-dir] (sync state and job history) and the
[data directory][data-dir] (downloaded guides, caches, and log files) separate volumes, set under
`persistence.state` and `persistence.data`. By default, state goes on a PersistentVolumeClaim and
data goes in an `emptyDir` volume, which lasts only as long as the pod. Losing the data directory
costs only a fresh download when the pod starts again. Put it on a claim to skip that download.

Both blocks take the same values:

| Value                | `state` default | `data` default  | Description                                                   |
| -------------------- | --------------- | --------------- | ------------------------------------------------------------- |
| `enabled`            | `true`          | `false`         | Use a PersistentVolumeClaim; `false` uses an `emptyDir`       |
| `existingClaim`      | none            | none            | Use this claim instead of creating one                        |
| `storageClass`       | none            | none            | StorageClass for the claim; none uses the cluster default     |
| `accessMode`         | `ReadWriteOnce` | `ReadWriteOnce` | Access mode for the claim                                     |
| `size`               | `1Gi`           | `2Gi`           | Size of the claim                                             |
| `labels`             | `{}`            | `{}`            | Labels for the claim the chart creates                        |
| `annotations`        | `{}`            | `{}`            | Annotations for the claim the chart creates                   |
| `emptyDir.sizeLimit` | none            | none            | Size limit of the `emptyDir`                                  |
| `emptyDir.medium`    | none            | none            | `Memory` uses a tmpfs, which counts against the memory limit  |

The `emptyDir` values apply only when `enabled` is `false`. The claim values apply only when it is
`true`. `labels` and `annotations` apply only to claims the chart creates, not to an
`existingClaim`. Use them, for example, for labels your backup tool selects on. The state claim
always keeps the chart's `helm.sh/resource-policy: keep` annotation, and
`persistence.state.annotations` cannot override it.

This example puts both directories on claims the chart creates with a specific StorageClass:

```yml
persistence:
  state:
    storageClass: ceph-block
  data:
    enabled: true
    storageClass: ceph-block
```

This one uses claims you created yourself:

```yml
persistence:
  state:
    existingClaim: my-recyclarr-state
  data:
    enabled: true
    existingClaim: my-recyclarr-data
```

State and data must use different claims. Both would mount the claim's root, and the server locks
each directory, so `helm install` fails if they point at the same claim.

Uninstalling the chart keeps the state claim it created, so a later install with the same release
name picks up the same state. Delete that claim yourself when you no longer need it. Uninstalling
deletes the data claim the chart created. Claims you set with `existingClaim` are yours, and the
chart never deletes them.

:::danger

With `persistence.state.enabled: false`, state lives in an `emptyDir` and is lost whenever the pod
is recreated. Recyclarr then no longer knows which Sonarr and Radarr resources it created (see
[State Directory][state-dir]).

:::

Unless the data directory is on a claim, log files are lost when the pod is recreated. Kubernetes
collects the server's console output, so you may want to turn off log files with
[`server.logging.files`][logging-files] in `settings.content`.

## Running CLI Commands {/*#cli*/}

The `recyclarr` CLI in the pod sends commands to the server in the same pod with the same API key,
so it needs no setup. `helm install` prints the exact command for your release:

```bash
kubectl exec deploy/recyclarr -- recyclarr sync --preview
```

## Network and Monitoring {/*#network*/}

The chart creates a Service with two ports:

| Port   | Name         | Serves                                             |
| ------ | ------------ | -------------------------------------------------- |
| `7982` | `http`       | The [HTTP API][api]                                |
| `7983` | `management` | Health probes (`/livez`, `/readyz`) and `/metrics` |

The chart creates no Ingress or HTTPRoute. The API is meant for clients inside the cluster, such as
the CLI in the pod or your own scripts. Change the API port on the Service with `service.port` (any
port except `7983`, which the management port uses), the Service type with `service.type`, and add
annotations, for example for a LoadBalancer implementation, with `service.annotations`. See
[Network Security][network-security] before you expose the API outside the cluster.

The pod has startup, liveness, and readiness probes on the management port. To have the Prometheus
Operator scrape [metrics][monitoring], set `serviceMonitor.enabled: true`. Set
`serviceMonitor.interval` to change the scrape interval and `serviceMonitor.labels` to add labels
your Prometheus selects on.

To export telemetry to an OpenTelemetry Collector, set the [OpenTelemetry variables][otel] in `env`:

```yml
env:
  - name: OTEL_EXPORTER_OTLP_ENDPOINT
    value: http://otel-collector.monitoring:4317
  - name: OTEL_RESOURCE_ATTRIBUTES
    value: deployment.environment=home
```

## Resources {/*#resources*/}

The chart sets no CPU or memory requests or limits by default. Usage depends on your configuration.
In one measurement, a server syncing one Sonarr and one Radarr instance (a few quality profiles and
guide custom formats) peaked at about 280Mi of container memory. About 150Mi of that was file cache
from the guide downloads, which the kernel can reclaim. Startup, including the guide download, used
under 3 CPU-seconds, and so did one sync of both instances. An idle server uses almost no CPU.
Larger configurations and more instances use more.

This is a reasonable starting point:

```yml
resources:
  requests:
    cpu: 50m
    memory: 256Mi
  limits:
    memory: 512Mi
```

It sets no CPU limit, because a CPU limit slows the first guide download, and the startup probe
gives that download 5 minutes.

## Other Values {/*#other-values*/}

The chart runs one replica with the `Recreate` update strategy, because only one server can use the
state volume at a time. With the default security contexts, the pod meets the Kubernetes Pod
Security `restricted` profile: it runs as the non-root UID and GID `1000` with the `RuntimeDefault`
seccomp profile, a read-only root filesystem, no privilege escalation, and all capabilities dropped.
The `helm test` pod runs the Recyclarr image with the same security contexts, so it passes in
namespaces that enforce that profile. Helm deletes a test pod that succeeds and keeps one that
fails, so you can read its logs, until the next test run.

`initContainers` and `extraContainers` add init containers and sidecars, using the standard
Kubernetes container spec. They can mount the chart's volumes by name (`data`, `state`, `tmp`,
`configs`, `includes`, `settings`) and any [extra volumes](#extra-volumes). The chart applies no
security context to them, so set one yourself if your namespace enforces a Pod Security profile.

`deploymentAnnotations` and `deploymentLabels` apply to the Deployment, and `podAnnotations` and
`podLabels` apply to the pod. Chart labels take precedence over both label values.

Other values follow common Helm chart conventions: `image`, `imagePullSecrets`, `nameOverride`,
`fullnameOverride`, `serviceAccount`, `podSecurityContext`, `securityContext`, `priorityClassName`,
`nodeSelector`, `tolerations`, and `affinity`. Recyclarr does not call the Kubernetes API, so
`serviceAccount.automount` defaults to `false` and the pod gets no API token. To see every value and
its default, run:

```bash
helm show values oci://ghcr.io/recyclarr/charts/recyclarr
```

## Without the Chart {/*#manifests*/}

If you write your own manifests, these are the parts the chart handles for you:

- Image `ghcr.io/recyclarr/recyclarr:9`. It runs as UID and GID `1000` and works with a read-only
  root filesystem when `/tmp` is a writable volume.
- Container ports `7982` (API) and `7983` (management). See [Monitoring][monitoring].
- `startupProbe` and `livenessProbe` on `/livez`, `readinessProbe` on `/readyz`, all on the
  management port. The server opens no port until the first guide download finishes, so give the
  startup probe several minutes.
- The API key in a Secret volume, with `RECYCLARR_API_KEY_FILE` set to the file path. Without a
  `subPath` mount, Kubernetes updates the file when the Secret changes, and the server uses the new
  key without a restart.
- Config files mounted read-only under `/config`, a PersistentVolumeClaim for the
  [state directory][state-dir] (`RECYCLARR_STATE_DIR`), and a separate volume for the
  [data directory][data-dir] (`RECYCLARR_DATA_DIR`), which can be an `emptyDir`.
- One replica with the `Recreate` strategy.

## Dev Chart {/*#dev-chart*/}

Each [dev image][dev-builds] has a matching dev chart. These are extremely unstable and not for
production Sonarr or Radarr instances. The dev chart for a branch has version `0.0.0-<branch>`, with
the branch name changed the same way as the image tag, and it defaults to that branch's dev image:

```bash
helm install recyclarr oci://ghcr.io/recyclarr/charts-dev/recyclarr \
  --version 0.0.0-master -f values.yaml
```

The image tag moves with each build, but the chart's default `image.pullPolicy` is `IfNotPresent`,
so a node keeps using the image it already pulled. Set `image.pullPolicy: Always` and restart the
pod to get the latest build. Dev chart versions follow the same [retention][dev-builds] as dev
images.
