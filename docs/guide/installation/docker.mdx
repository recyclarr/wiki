Recyclarr has an official Docker image hosted on the following platforms:

| Registry                                 | Image Name                    |
|------------------------------------------|-------------------------------|
| [Github Container Registry (GHCR)][ghcr] | `ghcr.io/recyclarr/recyclarr` |
| [Docker Hub][dockerhub]                  | `recyclarr/recyclarr`         |

:::info

This guide refers exclusively to the GHCR image, but all steps apply equally to the Docker Hub
image. Adjust the image name as needed.

:::

[ghcr]: https://github.com/recyclarr/recyclarr/pkgs/container/recyclarr
[dockerhub]: https://hub.docker.com/r/recyclarr/recyclarr

## Docker Compose Example {/*#docker-compose-example*/}

The examples on this page use `docker compose` with a `docker-compose.yml` file, which is the
recommended approach for managing container configuration in one place.

:::warning

The example below should not be used verbatim. Copy and paste it, then make the appropriate changes
for your specific use case.

:::

```yml
networks:
  recyclarr:
    name: recyclarr
    external: true

services:
  recyclarr:
    image: ghcr.io/recyclarr/recyclarr:9
    container_name: recyclarr
    restart: unless-stopped
    user: 1000:1000
    networks: [recyclarr]
    volumes:
      - ./config:/config
    environment:
      - TZ=America/Santiago
```

The container runs the Recyclarr server. The server stays running, syncs on a
[built-in schedule](#scheduling), and accepts commands from the [CLI](#cli). Start it in the
background:

```bash
docker compose up -d
```

Here is a breakdown of the above YAML:

- `networks`<br/>
  Recyclarr needs network access to Sonarr and Radarr instances. How those services are hosted
  determines the network configuration. This example uses a dedicated Docker bridge network (named
  `recyclarr`) shared with those services, allowing Recyclarr to reach them directly without going
  through a reverse proxy.
- `image`<br/>
  The official Recyclarr image, hosted on Github. The `:9` tag receives all feature and bugfix
  updates within major version 9. See [Tags](#tags) for other options.
- `container_name`<br/>
  Optional. Prevents Docker Compose from generating a prefixed name like `prefix_recyclarr`.
- `restart`<br/>
  Starts the server again after a crash or a reboot of the host. Without a restart policy, scheduled
  syncs stop until you start the container yourself.
- `user`<br/>
  Optional user and group ID for the container process. Recyclarr runs as this UID:GID, and any
  files it creates in the `/config` volume are owned by this user and group. Defaults to `1000:1000`
  if not specified.

## Tags {/*#tags*/}

Docker tags represent components of the semantic version number following the format `X.Y.Z`, where:

- `X`: Represents a *major* release containing breaking changes.
- `Y`: Represents a *feature* release.
- `Z`: Represents a *bugfix* release.

The following table describes the available tags. Using `v2.1.2` as an example, the table is sorted
by *risk* in descending order. For maximum *stability*, use the bottom row. For the most automatic
updates (highest risk), use the top row.

| Tag     | Description                                                             |
|---------|-------------------------------------------------------------------------|
| `2`     | Latest *feature* and *bugfix* release; manual update for major releases |
| `2.1`   | Latest *bugfix* release; manual update if you want new features         |
| `2.1.2` | Exact release; no automatic updates                                     |

The **recommended tag** is the major version number (e.g. `9`), which gives you all feature and
bugfix releases automatically while requiring a manual update only for breaking changes.

There is no `latest` tag. It would move to each new major release automatically and apply breaking
changes without warning, which causes problems that reading the [upgrade guide][upgrade-guide] and
release notes first would have prevented. A major version tag lets you decide when to upgrade.

:::info

All docker tags described here are *mutable* with the exception of the three-component version
number (e.g. `2.1.2` in the table above). A *mutable tag* is one that may change with each release
of Recyclarr.

:::

### Edge (Dev) Builds {/*#edge-warning*/}

:::danger

The `edge` tag should be considered **extremely unstable**. It contains unreleased code on the
`master` branch and most likely has bugs.

This tag should **not** be used just to get the latest features. It is intended for testing new
features prior to the next release and should not be run against production instances of Radarr or
Sonarr.

*Use this tag at your own risk!*

:::

A *mutable* docker tag named `edge` is also available. It contains the absolute latest code changes
on the `master` branch. This is the most volatile and risky tag. Only use it with full understanding
of the consequences.

## Configuration {/*#configuration*/}

### Volumes {/*#volumes*/}

- `/config`<br/>
  The default directory for all Recyclarr files: configuration, state, logs, and downloaded
  resources. Server logs are written to `/config/logs/server/`. `docker logs recyclarr` also shows
  the server's log output.

<details>
<summary>Separating config from data for backups</summary>

Recyclarr supports splitting its files into a **config directory** (user configuration, state) and a
**data directory** (logs, downloaded resources). This lets you back up only the config directory
while treating data as disposable.

```yml
services:
  recyclarr:
    image: ghcr.io/recyclarr/recyclarr:9
    container_name: recyclarr
    restart: unless-stopped
    user: 1000:1000
    environment:
      - TZ=America/Santiago
      - RECYCLARR_CONFIG_DIR=/config
      - RECYCLARR_DATA_DIR=/data
    volumes:
      - ./recyclarr:/config      # back this up
      - recyclarr_data:/data     # ephemeral, no backup needed
volumes:
  recyclarr_data:
```

With this setup, `/config` holds user configuration and state (back this up), while `/data` holds
only regenerable files. See [File Structure][file-structure] for details on what lives in each
directory.

</details>

### Environment {/*#docker-env*/}

:::info

The `PUID` and `PGID` environment variables are **not** supported by the official Recyclarr Docker
image. These are not built-in Docker features.

Recyclarr's Docker container is **rootless**. Use the `user` property (in Docker Compose) or the
`--user` option (with the Docker CLI) to specify the user and group IDs.

:::

- `TZ` (Default: `UTC`)<br/>
  The time zone for Recyclarr's local time in the container. The [sync schedule](#scheduling) uses
  this time zone.

- `RECYCLARR_CONFIG_DIR` (Default: `/config`)<br/>
  Override the config directory path inside the container. See [Environment Variables][env-config].

- `RECYCLARR_DATA_DIR` (Default: same as `RECYCLARR_CONFIG_DIR`)<br/>
  Override the data directory path inside the container for ephemeral files (resources, logs). See
  [Environment Variables][env-data].

## Configuration Changes {/*#config-changes*/}

The server reads your YAML configuration and `settings.yml` once, when it starts. If the
configuration is not valid, the server does not start. After you edit any of these files, restart
the container:

```bash
docker compose restart recyclarr
```

## Scheduling {/*#scheduling*/}

By default, the server syncs every configured Sonarr and Radarr instance once a day at midnight,
using the time zone set by `TZ`. To change when syncs run, set
[`server.schedule.cron`][schedule-cron] in `settings.yml`:

```yml
server:
  schedule:
    cron: 0 4 * * *  # Every day at 4:00 AM
```

See [`server.schedule`][schedule] for how the server handles overlapping and missed syncs.

### Using an External Scheduler {/*#external-scheduler*/}

To start syncs from another scheduler instead (for example, cron on the host), turn off the built-in
schedule:

```yml
server:
  schedule:
    enabled: false
```

Then have your scheduler run the sync command through `docker exec`:

```bash
docker exec recyclarr recyclarr sync
```

The scheduler can also start syncs through the [HTTP API](#http-api) instead.

## Running CLI Commands {/*#cli*/}

The image includes the `recyclarr` CLI. Run it with `docker exec` while the container is running.
The CLI sends each command to the server in the same container, so the server must be running. See
[Client and Server][client-server] for how the CLI and server work together.

Using Docker Compose:

```txt
docker compose exec recyclarr recyclarr [command] [options]
```

Or using Docker directly:

```txt
docker exec recyclarr recyclarr [command] [options]
```

Examples:

```bash
# Sync Sonarr and show debug logs
docker exec recyclarr recyclarr sync sonarr --log debug

# Do a preview (dry run) sync for Radarr
docker exec recyclarr recyclarr sync radarr --preview
```

Syncs you start this way wait in the same queue as scheduled syncs. See the [CLI reference][cli] for
all commands.

## HTTP API {/*#http-api*/}

The server listens on port `7982` inside the container. The CLI inside the container does not need
this port published. To call the API from outside the container, publish the port in your compose
file:

```yml
services:
  recyclarr:
    ports:
      - 7982:7982
```

To use a different port on the host, change the first number (for example, `8000:7982`). See the
[API reference][api] for the available endpoints.

:::danger

The API has no authentication. Anyone who can reach the published port can start syncs and delete
custom formats in your Sonarr and Radarr instances. Do not publish the port to an untrusted network.

:::

## Health Check {/*#health-check*/}

The image has a built-in Docker health check. It requests `/health` from the server every 30 seconds
and marks the container unhealthy when the server does not respond. `docker ps` and
`docker compose ps` show the result.

## Stopping the Container {/*#stopping*/}

When the container stops, the server cancels any sync that is running. Changes already applied to
Sonarr or Radarr stay in place. Queued syncs do not run when the container starts again.

## Advanced Configuration {/*#advanced-configuration*/}

### Read-Only Container {/*#read-only-container*/}

For additional security, the [container filesystem can be made read-only][read_only]. This requires
two changes in Docker Compose:

1. Add the `read_only: true` setting to the service configuration.
1. Mount `/tmp` (inside the container) to a volume. This path must be writable for Recyclarr to run.
   Using `tmpfs` is recommended since these files are temporary by design, and keeping them in
   memory offers some performance benefits.

Using the example `docker-compose.yml` from the top of this page, add the following:

```yml
services:
  recyclarr:
    image: ghcr.io/recyclarr/recyclarr:9
    read_only: true # <-- Add this to enable read-only mode
    tmpfs: /tmp # <-- Mount /tmp to a volume
    # ...
```

### Prevent in-container privilege escalation {/*#prevent-in-container-privilege-escalation*/}

For additional security, [run Recyclarr with `--security-opt=no-new-privileges`][security_opt] to
prevent privilege escalation. This prevents the container from gaining new privileges via `setuid`
and `setgid` binaries like `su` and `sudo`.

Add `security_opt: ['no-new-privileges:true']` to the service configuration:

```yml
services:
  recyclarr:
    image: ghcr.io/recyclarr/recyclarr:9
    security_opt: ['no-new-privileges:true'] # Add this line
    # ...
```
